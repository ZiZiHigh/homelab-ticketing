STEP 02 - Build, start and verify the osTicket Compose stack

CONTEXT
The image audit was finished. The application image and the MariaDB image
were already pinned by digest. The next job was to build the Compose stack,
start it inside the homelab Docker network, and verify that the application
could install itself and serve the agent login before I touched nginx or DNS.

The host is the same old laptop. It runs the existing 7 homelab containers
and the Samba AD DC. The reverse proxy is the container
`homelab-nginx-nginx-1`. The shared network is `172.20.0.0/16`. The host has 3.7 GiB RAM and the stack has to fit
next to the existing services. The new stack may not publish a host port.
The database must not be reachable from other containers on the `homelab`
network.

The public name is still `http://tickets.home.arpa`, but DNS and the nginx
vhost are not part of this step. The internal test used the Compose service
name `osticket:8080`. HTTPS and email remain out of scope.

The application image is:

    hlhd/osticket:v1.18.4@sha256:d115c1a73cafb790ca730e8805178c92484974ceab4f6109dd2a6c71b55e68f4

The database image is:

    mariadb:11.8.9@sha256:f16d7a344413e519dff518f27bdb221388f84b0d274c97c4fb5f2cb0dc1b34fa

I used `sudo -n docker` because the normal login user is not in the docker
group. The project sudo rule allows Docker without a password. All repository
files are written in English. Commands and outputs below are copied from the
session. Secret values are not included.

B2 - First start

        sudo -n docker compose up -d

    The first timestamp was `2026-10-21T12:38:55+02:00`. Docker created

12. The app did not become healthy. The health status went from `starting` to

        ticket-system-osticket-1 ... Restarting (1) 41 seconds ago

    `docker inspect` reported `RestartCount=11`. The DB stayed healthy.

13. Read the app log. The repeating error was:

        [install-seed] running osTicket Installer (schema + admin user + defaults)
        [install-seed] install FAILED:
          - username: Bad username

    The entrypoint was loading the three file-based secrets correctly. The
    failure was after the database connection, during the installer's form
    validation.

14. Checked the database before changing anything. `SHOW TABLES` returned no
    rows and `SELECT ... FROM ost_staff` failed with:

        ERROR 1146 (42S02) at line 1: Table 'osticket.ost_staff' doesn't exist

    The failed install had not left a partial schema or a partial admin row.
    The database volume was fresh and safe to reuse.

15. Searched the image source for the error string:

        grep -RIn "Bad username" /var/www/html

    The hit was in `setup_hidden/inc/class.installer.php`. The relevant code
    was:

        if(!$this->errors['username'] && in_array(strtolower($vars['username']),array('admin','admins','username','osticket')))
            $this->errors['username']=__('Bad username');

    The username validator itself accepts `admin` because it has more than two
    characters and only valid characters. The separate blocklist rejects the
    exact predictable names `admin`, `admins`, `username` and `osticket`.
    Because the check uses `strtolower`, changing the case to `Admin` would
    not help.

16. Backed up the local environment files:

        cp -a .env .env.bak-2026-10-21-1241
        cp -a .env.example .env.example.bak-2026-10-21-1241

    Changed `ADMIN_USER=admin` to `ADMIN_USER=homelab-admin` in both files and
    added a comment that explains the blocklist. The rest of the configuration
    stayed unchanged.

17. Ran `docker compose config --quiet`, then `docker compose up -d` again.
    Compose recreated only the application container. The database container
    stayed running. The app became healthy at `12:42:02`. The log showed:

        [install-seed] osTicket installed: schema loaded, admin "homelab-admin" created.

18. Verified the running system. The checks are listed in the next section,
    because the verification is the part that matters for the next step.

WHAT WENT WRONG

Problem 1: the read-only tmpfs mount was not writable by uid 1000.

Exact error:

    mkdir: can't create directory '/run/osticket/nginx/': Permission denied
    mkdir: can't create directory '/run/osticket/php': Permission denied
    rc=1

Cause: Docker mounts an anonymous tmpfs as root:root with mode 755 unless
the mount options say otherwise. The image's normal `/run/osticket` is owned
by uid 1000 and is group-writable, but a tmpfs mount replaces that directory
with a new empty filesystem. The entrypoint therefore could not create its
nginx temp directories or its PHP ini.

Fix: add `uid=1000,gid=0,mode=770` to the `/run/osticket` tmpfs and
`mode=1777` to `/tmp`. The test then showed the directory owned by
`osticket:root` with mode 770 and the probe file was created.

Problem 2: the first install used a username that osTicket rejects.

Exact error:

    [install-seed] install FAILED:
      - username: Bad username

Cause: osTicket's installer has a hard-coded blocklist for the exact names
`admin`, `admins`, `username` and `osticket`. This is not a database error,
not a password error and not a container error. The installer runs inside the
app container and exits with status 1. Docker then restarts the container
because the restart policy is `unless-stopped`, so the same error repeats.

Fix: use a different local admin username. I chose `homelab-admin`. The
admin password stayed the same. The app recreated and completed the install.

Problem 3: the first start left no schema, but that was expected after the
validation failure. `SHOW TABLES` was empty and `ost_staff` did not exist. I
did not remove the database volume. The next install ran against the same
empty database and succeeded.

Problem 4: one verification command ran outside the Compose directory. The
command was `docker compose ps` in a shell that did not set the working
directory. Compose returned:

    no configuration file provided: not found
    Exited with code 1

The stack was not broken. Compose simply looked for `docker-compose.yml` in
the home directory. I reran the same check from `~/ticket-system/compose` and
it worked. The mistake was in the shell invocation, not in the stack.

Known warnings that were not failures:

- The app logs this on every start:

      nginx: [alert] could not open error log file: open() "/var/lib/nginx/logs/error.log" failed (30: Read-only file system)

  The root filesystem is read-only. The rendered nginx config logs to
  `/dev/stderr`, so the real access log still appears in `docker compose logs`.
  The alert comes from nginx trying to open its compiled-in default error log
  before it reads the rendered config. The app is healthy and serves requests.

- MariaDB logs:

      [Warning] mariadbd: io_uring_queue_init() failed with EPERM
      create_uring failed: falling back to libaio

  The host has `kernel.io_uring_disabled=2`, so MariaDB falls back to
  `libaio`. The database started and passed its healthcheck. This is a host
  setting, not a stack setting, and I did not change it.

- MariaDB also logs that `/sys/fs/cgroup///memory.pressure` is not writable.
  The container still starts and the healthcheck passes. I left it alone.

WHAT I ASSUMED WRONGLY

1. I assumed `ADMIN_USER=admin` was a valid local username. The osTicket
   installer rejects it on purpose. The validation is separate from the
   normal username character check. I should have read the installer's
   username rules before choosing the first admin account.

2. I assumed that setting `character-set-server=utf8mb4` in `mariadb.cnf`
   would make the osTicket database and tables use utf8mb4. It did not. The
   osTicket installer runs:

       ALTER DATABASE <name> DEFAULT CHARACTER SET utf8 COLLATE utf8_general_ci

   and `install-mysql.sql` creates tables with `DEFAULT CHARSET=utf8`. On
   MariaDB 11.8 those names resolve to utf8mb3. The server variables are
   utf8mb4, but the database and tables are utf8mb3 with table collation
   `utf8mb3_uca1400_ai_ci`. I did not convert the tables. A broad conversion
   would change the upstream schema and could hit index or column limits. I
   recorded it as a known limitation instead.

3. I assumed a tmpfs mount would inherit the image directory ownership. It
   does not. Docker creates it fresh with root ownership. The mount options
   have to set `uid`, `gid` and `mode` explicitly.

4. I assumed the `PORTS` column in `docker compose ps` would make it obvious
   whether a port is published. It lists the image's exposed ports as
   `8080/tcp` and `9000/tcp`, but those are not host bindings. The reliable
   checks are `docker port <container>` and `.HostConfig.PortBindings`. Both
   were empty or `{}`.

5. I assumed the first `docker compose up -d` would be the end of the start.
   It was not. The application's own installer validation failed after the
   database was already healthy. The container healthcheck did its job and
   made the loop visible instead of leaving a half-started web server.

DEAD ENDS

- Trying `Admin` instead of `admin` would not work. The installer lowercases
  the name before the blocklist check. I confirmed this in the source and did
  not spend a restart on it.

- Patching `class.installer.php` inside the container, or replacing the
  `setup_hidden` tree, would make the local deployment diverge from the
  audited image digest. It would also be lost on every container recreate.
  I rejected that path. The configuration value is the supported fix.

- Making the root filesystem writable to get around the tmpfs error would
  remove one of the main hardening controls. I rejected it. The mount options
  fixed the actual problem without weakening the container.

- Removing the database volume to force a clean install was not necessary.
  The failed install had not created any tables. Removing the volume would
  have destroyed the only copy of the database for no reason.

- Converting every osTicket table to utf8mb4 was considered and not done.
  The upstream installer explicitly chooses utf8, and the schema is part of
  the audited release. I would need a tested migration and a backup before
  changing it.

HOW I DIAGNOSED IT

The first signal was the health state, not the HTTP port. `docker compose ps`
showed the database healthy and the app restarting. `docker compose logs
osticket` showed the installer error. I did not guess from the container
status alone.

I then searched the image for the exact error string and read the installer
around the hit. That showed the blocklist and explained why a normal username
validator would accept `admin` while the installer would not. I also checked
`strtolower` in the condition, which ruled out a case-only change.

Before changing the environment, I checked the database state. `SHOW TABLES`
returned nothing and `ost_staff` did not exist. That told me the failed run
had not written a partial schema and that reusing the volume was safe.

For the tmpfs problem, I ran the same image with the same read-only and tmpfs
flags and asked it to create the directories directly. The permission error
was immediate. I checked `id` and `ls -ld /run/osticket` inside the test
container. The user was uid 1000 and the tmpfs was root:root 755. The mount
options were the cause, not the entrypoint.

For the charset mismatch, I used `SHOW CREATE DATABASE` and `SHOW CREATE
TABLE ost_ticket`, then compared them with the installer source. The server
variables and the schema were different on purpose. That changed the finding
from "my config did not apply" to "the application explicitly overrides it".

HOW I FIXED IT

1. Added the tmpfs ownership options to `compose/docker-compose.yml`:

       /run/osticket:rw,noexec,nosuid,size=64m,uid=1000,gid=0,mode=770
       /tmp:rw,noexec,nosuid,size=64m,mode=1777

2. Backed up `.env` and `.env.example`, changed `ADMIN_USER` to
   `homelab-admin`, and added a comment about the osTicket blocklist.

3. Ran `docker compose config --quiet`, then `docker compose up -d`. Compose
   recreated the app container and left the database container and volume
   alone.

4. Did not patch the image, did not make the root filesystem writable, did
   not remove the database volume, and did not convert the schema charset.

ROLLBACK

Stop the stack without deleting data:

    cd ~/ticket-system/compose
    sudo -n docker compose stop

Remove the containers and the internal network but keep the named volume:

    cd ~/ticket-system/compose
    sudo -n docker compose down

The volume `ticket-system-db-data` stays after `down`. That is intentional.
Do not run `docker compose down -v` and do not remove the volume without
explicit approval, because it contains the tickets and the admin account.

To undo only the application container after a bad environment change:

    cd ~/ticket-system/compose
    sudo -n docker compose up -d --force-recreate osticket

To restore the pre-fix environment files for forensics:

    cp .env.bak-2026-10-21-1241 .env
    cp .env.example.bak-2026-10-21-1241 .env.example

That restore puts `ADMIN_USER=admin` back and the installer will fail again.
It is not a working rollback, only a way to get the old file back.

The nginx config, DNS records and Samba AD were not changed in this step, so
there is nothing to undo there. No host port was opened.

LESSON LEARNED

The installer's own validation is part of the application behaviour. A
container can be healthy at the infrastructure level, connected to a healthy
database, and still fail because the application rejects one form value.
Read the installer rules before choosing the first admin account, especially
when the value is a default like `admin`.

A tmpfs is a new filesystem. It does not inherit the ownership of the
directory it covers. When a container runs as a non-root user, the mount
options need `uid`, `gid` and `mode` that let that user write.

Server charset settings are not the same as application schema settings. I
checked the actual `SHOW CREATE DATABASE` and `SHOW CREATE TABLE` output
instead of trusting `character_set_server`.

The healthcheck and the restart count were more useful than the container
status alone. They showed a repeating application failure and gave me a
reason to read the logs immediately.

File-based secrets worked as intended. The logs only said that the entrypoint
loaded each secret from its file. The values never appeared in the compose
file, the environment, the logs or the repository.

The database volume survived the app recreate. That is the right separation:
application config can be recreated, data must not be. I did not use the
volume as a debugging toy.

A first start is not verified until the login works and a restart keeps the
data. HTTP 200 on the login page alone would not have proved that the admin
account was usable.
