STEP 05 - Rotate the admin password during the Access denied investigation

NOTE (2026-10-21, corrected after user confirmation): The rotation did not fix
the login. The actual cause was the client sign-in form at `/login.php`; staff
use `/scp/login.php`. The rotation was done before that was clear. It remains
in place: the current 20-character password works on the agent form and the old
32-character password is no longer valid. The corrected diagnosis is in
STEP 04.

CONTEXT
The main PC could open `http://tickets.home.arpa`, but the user got
`Access denied` with the username `homelab-admin`. The old 32-character value
from `compose/secrets/admin_password.txt` authenticated from the server with
status 302, but the user could not authenticate from either browser. The user
had copied the value from a local `.txt` file, from `nano` and from `cat`.

The old credential was valid on the server, so nginx, DNS and the database
connection were not the problem. After several failed client-side attempts,
the user approved a password rotation. The goal was to set a new value that is
easier to copy or type and to leave the database hash and the local secret
file in sync.

The new password is not printed in this journal. The secret file is mode 600.
Only its shape and the verification results are recorded here.

WHAT I TRIED

1. Re-checked the old state before changing anything:
   - `ost_staff` row: `staff_id 1`, `homelab-admin`, `isactive 1`,
     `isadmin 1`, `change_passwd 0`.
   - Old secret file: 32 bytes, no trailing newline, no edge whitespace.
   - Old password from the server on `/scp/login.php`: AJAX login returned
     `status:302`.
   - Old password plus a trailing space or newline: `status:401` with
     `Access denied`.
   This confirmed that the old credential was valid server-side and that the
   remaining problem was in the client input path.

2. Inspected the osTicket password implementation before writing a hash:
   - `include/class.staff.php` `check_passwd()` calls `Passwd::cmp()`.
   - `include/class.passwd.php` uses `include/PasswordHash.php` (phpass).
   - The old database hash started with `$2a$` and was 60 characters.
   - `Passwd::hash($password, $work_factor)` produces a compatible bcrypt
     hash.
   - A self-test with a dummy password at cost 12 returned prefix `$2a$`,
     length 60 and `verify=ok`. I did not use PHP `password_hash()` because
     osTicket uses its own phpass wrapper.

3. Backed up the old secret file to
   `compose/secrets/admin_password.txt.bak-2026-10-21-1406` with mode 600.
   The old database hash was kept only in a mode-600 temporary file for
   rollback. Neither value was printed.

4. Generated a new 20-character password from lowercase letters and digits,
   excluding `i`, `l`, `o`, `0` and `1`. Wrote it to a mode-600 temporary
   file with no trailing newline.

5. Generated the new hash inside the app container with osTicket's own
   `Passwd::hash($new, 10)`. The result started with `$2a$` and was 60
   characters. The helper script also ran `Passwd::cmp($new, $hash, 10)` and
   it returned ok before the DB update.

6. Updated `ost_staff.passwd` for `staff_id 1` and set `change_passwd = 0`.
   The SQL was read from a mode-600 temporary file, not passed on the command
   line.

7. Replaced `compose/secrets/admin_password.txt` in place with the new
   20-byte value and set mode 600. Writing in place kept the Docker Compose
   secret bind mount in sync; `/run/secrets/admin_password` inside the app
   container also reported 20 bytes.

8. Verified the new login through `http://tickets.home.arpa` with the same
   AJAX request the agent form uses. The new value returned `status:302` and
   updated `lastlogin`. The old backup returned `status:401` with
   `Access denied`.

9. The user still got `Access denied` from the top-right "Sign In" form with
   the new password. The user then used "I'm an agent - sign in here" and the
   same new password worked. The page links explained it: the top-right link
   is `/login.php` (client portal), the agent link is `/scp/`.

WHAT WENT WRONG

- The first automation attempt exited with code 141 before changing anything.
  The command was:

      tr -dc '...' < /dev/urandom | head -c 20 > new_password

  With `set -o pipefail`, `head` closed the pipe after 20 bytes, `tr` received
  SIGPIPE and the pipeline reported 141. I checked the database hash, the
  secret file and `lastlogin`; they were unchanged. I then ran it again with
  pipefail disabled for that one pipeline.

- The second attempt failed at:

      docker compose cp new_password osticket:/tmp/new_password

  with:

      Error response from daemon: container rootfs is marked read-only

  The app container has a read-only root filesystem. I checked that the
  database hash and the secret file were unchanged, then used stdin instead:

      docker compose exec -T -u root osticket sh -c \
        'umask 077; cat > /tmp/new_password' < new_password

  The same method copied the temporary PHP hasher into `/tmp`. `/tmp` is a
  writable tmpfs.

- The old 32-character password worked from curl on the agent endpoint but
  not from the user's browser. The browser was on the client form. Rotation
  was not the fix, and it changed a working credential unnecessarily. The new
  password is still valid and is now the documented credential.

WHAT I ASSUMED WRONGLY

1. I assumed the user was on the agent login form. The browser was on
   `/login.php`, the client portal. The top-right "Sign In" link goes there.

2. I assumed the browser was sending a different value than the file. The
   server-side test proved the value was valid. The difference was the
   endpoint, not the password.

3. I assumed a password rotation was a reasonable next step before confirming
   the exact URL and form. That was the wrong order.

4. I assumed `docker compose cp` would work in a hardened container. The app
   root filesystem is read-only; only `/tmp` is writable.

5. I assumed `set -o pipefail` was safe for a generator pipeline. It turned a
   harmless SIGPIPE from `head` into a failed step.

6. I did not assume that PHP `password_hash()` would be compatible with
   osTicket. The application uses its own `PasswordHash` wrapper, so I used
   `Passwd::hash()` instead of guessing.

DEAD ENDS

- Asking for another exact copy of the old 32-character value was a dead end.
  The user tried a local `.txt` file, `nano` and `cat`; the browser still
  returned `Access denied` because it was the client form.

- Re-checking nginx, DNS and the database was a dead end. The old credential
  already authenticated server-side and the stack was healthy.

- Using PHP `password_hash()` would have introduced an unnecessary
  compatibility question. osTicket uses `Passwd::hash()` from
  `class.passwd.php`.

- `docker compose cp` was a dead end because of the read-only container
  rootfs. The working path was `docker compose exec` with stdin.

- Rotating the password was a dead end for the original login failure. It
  changed the credential but did not change the form the browser was using.

HOW I DIAGNOSED IT

I separated the credential from the client. The old secret returned 302 from
the server on `/scp/login.php` and updated `lastlogin`, so the account and the
hash were valid. A trailing space or newline returned 401. The user still
could not authenticate after multiple copy methods, so I rotated the password
instead of changing DNS, nginx or the browser again.

The missing piece was the page URL. The top-right "Sign In" link goes to
`/login.php` and the client page contains "I'm an agent - sign in here" pointing
to `/scp/`. The user confirmed that the agent link works. That proved the
client form was the problem. The rotation procedure was technically correct,
but it was not the fix.

Before writing the new hash I checked the actual login code.
`Staff::check_passwd()` calls `Passwd::cmp()`, and `Passwd` uses
`include/PasswordHash.php`. The existing hash was `$2a$` and 60 characters. I
used the same hasher for the new value. A self-test with a dummy password
returned prefix `$2a$`, length 60 and `verify=ok`.

HOW I FIXED IT

1. Backed up the old secret file and saved the old hash in a mode-600 temp
   file.
2. Generated a 20-character password with lowercase letters and digits,
   excluding `i`, `l`, `o`, `0` and `1`, with no newline.
3. Generated the hash with:

       Passwd::hash($new, 10)

   and checked it with:

       Passwd::cmp($new, $hash, 10)

4. Updated the database row:

       UPDATE osticket.ost_staff
       SET passwd = '<new hash>', change_passwd = 0
       WHERE staff_id = 1;

   The hash was read from a mode-600 SQL file and was not printed.
5. Replaced `compose/secrets/admin_password.txt` in place with the new value
   and set mode 600.
6. Verified the new login through nginx on `/scp/login.php`, then checked that
   the old backup returned 401.
7. Corrected the login procedure: use the agent link, not the top-right client
   form. The password change stays because it is already in place and the new
   value is verified.

The new password is available only in
`compose/secrets/admin_password.txt`. It is 20 characters, lowercase letters
and digits, with no trailing newline. It is not in this journal, the README,
the changelog or Git.

HOW I VERIFIED IT

- New secret shape: 20 bytes, 20 characters, mode 600, no edge whitespace.
- Container secret: `/run/secrets/admin_password` reported 20 bytes.
- Database row: `staff_id 1`, `homelab-admin`, `isactive 1`, `isadmin 1`,
  `change_passwd 0`, hash prefix `$2a$`, hash length 60.
- New login on `/scp/login.php`: HTTP 200 with JSON `"status":302`.
- `lastlogin` changed to `2026-10-21 14:06:53`.
- Old backup login: HTTP 200 with JSON `"status":401` and
  `"message":"Access denied"`.
- User browser: the top-right client form still rejects the staff account; the
  "I'm an agent - sign in here" link accepts the current password.
- Services: `ticket-system-db-1` healthy, `ticket-system-osticket-1`
  healthy.

ROLLBACK

The old secret file is backed up at
`compose/secrets/admin_password.txt.bak-2026-10-21-1406` with mode 600. The
old database hash was kept only in a mode-600 temporary file and was removed
after the successful verification.

To roll back:

1. Generate a hash of the old password with osTicket's `Passwd::hash()`.
2. Update `ost_staff.passwd` for `staff_id 1` with that hash.
3. Copy the old secret backup back to `compose/secrets/admin_password.txt`
   and set mode 600.
4. Verify login and `lastlogin`.

Do not restore only the file or only the database hash.

LESSON LEARNED

Confirm the exact login URL and form before rotating a credential. osTicket has
separate client and agent logins. The top-right "Sign In" is for clients;
staff use `/scp/login.php` or the "I'm an agent - sign in here" link.

A password rotation is not a diagnosis. In this case the old password was
valid. The rotation changed the credential but did not fix the original
failure. Keep the rotation because it is already verified, but do not present
it as the root cause.

osTicket 1.18.4 uses phpass through `Passwd::hash()` and `Passwd::cmp()`, not
PHP's `password_hash()` directly. Use the application's hasher when changing a
password in the database.

A hardened container can have a read-only root filesystem even when `/tmp` is
writable. Use `docker compose exec` with stdin and a umask-protected file in
`/tmp` instead of `docker compose cp`.

`set -o pipefail` turns a normal SIGPIPE from `generator | head` into a failed
step. Disable pipefail for that pipeline or generate the value another way.

Keep the database hash and the secret file in sync. Verify both the new value
and the old value after rotation. The old value should no longer authenticate.
